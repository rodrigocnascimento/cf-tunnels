## Overview

This document exists to **not lose an idea**, not to propose a plan. It records a
design conversation about whether `cftunnel` should eventually be able to
manage tunnels whose ingress configuration lives in Cloudflare's control
plane ("remotely-managed" tunnels) instead of only the local-YAML model
(`cloudflared tunnel run --config local.yml`, "locally-managed") that
`cftunnel` exclusively supports today.

**Nothing here is decided.** No code changes, no version bump, no
implementation timeline. Unlike CFTUNNEL-010 (which specifies a concrete,
buildable contract for a deferred feature), this document is one level more
speculative: it exists because the idea is good enough to be worth not
losing, and because the conversation that produced it was explicitly both
technical and philosophical — the second part doesn't fit in a code diff and
would otherwise evaporate.

### Why this is not a normal TDD

Every other `spec/tdd-*.md` in this repository either documents a shipped
change or a fully-specified deferred one (CFTUNNEL-010). This one is neither.
It is closer to a decision-journal entry: capturing the reasoning, the
trade-offs, and the open questions at the point they were raised, so that
whoever picks this up next — possibly the same two people, months later —
does not have to re-derive the reasoning from scratch or, worse, re-litigate
settled sub-points as if they were new.

## Origin and Motivation

An external review (Gemini) of this project raised four criticisms:
resource overhead of one `cloudflared` process per tunnel, systemd/Linux
lock-in, weaker disaster recovery than Terraform or a fully remote-managed
setup, and a general observation that the industry has moved toward
remote-managed configuration. Working through each critique concretely (see
the conversation this document was drafted from) produced measured, mostly
reassuring answers for the first point and an explicit decision to leave the
second out of scope. The disaster-recovery point held up under scrutiny,
however: the per-tunnel credential file (`<UUID>.json`) generated by
`cloudflared tunnel create` is **not recoverable** once lost — losing the
host without a backup means deleting and recreating that tunnel, which
changes its UUID and therefore its DNS target.

Investigating what Cloudflare itself offers as the alternative turned up a
concrete, verifiable fact: for a remotely-managed tunnel, the connector
token **can be rotated/refreshed via the dashboard or API without deleting
the tunnel**, and existing connections keep working until the connector is
restarted with the new token. That is a materially better disaster-recovery
property than anything achievable by backing up the current local credential
model harder — it doesn't need a backup at all in the same sense, because
the thing that would be lost is regenerable by design.

That single fact is what elevated this from "yet another criticism to
answer" to "a direction worth recording on purpose."

## Philosophical Considerations

This section exists because the conversation that produced this document
explicitly identified the choice as not purely technical.

### What `cftunnel` currently optimizes for

Every prior TDD in this repository — CFTUNNEL-002 (zone isolation),
CFTUNNEL-004 (critical bug fixes), CFTUNNEL-007 (safe credential binding),
CFTUNNEL-008 (fail-closed discovery), and the locale-collation hardening in
CFTUNNEL-009 — optimizes for the same underlying value: **the local
filesystem is the source of truth, and every operation must be safe, legible,
and auditable without trusting anything cftunnel doesn't itself verify.**
That value is not incidental; it is the reason this project exists instead
of the user simply running `cloudflared tunnel login && cloudflared tunnel
create` by hand, or the official `cloudflared service install <TOKEN>`
one-liner Gemini's review pointed to.

### What a control-plane-backed mode would trade away

Moving ingress configuration into Cloudflare's control plane means the
"source of truth" for what hostnames route where is no longer a file you can
`cat`, `diff`, or back up independently of Cloudflare's availability and
continued cooperation. It is a deliberate trade of local verifiability for
operational convenience and disaster-recovery robustness. This is the same
axis Gemini's review named ("cloud is just someone else's computer") — the
review treated it as a one-way trade cftunnel had implicitly rejected;
this conversation treats it as an axis cftunnel could let the *user* choose
per tunnel, rather than a decision the tool makes for them once.

### Why "additive" matters philosophically, not just technically

An earlier framing in this conversation (for the TUI integration work,
CFTUNNEL-010) established a pattern worth repeating here: don't force a
project to pick one identity when it can offer both and let the operator
choose based on what a specific tunnel needs. A tunnel fronting a
throwaway homelab dashboard has different disaster-recovery stakes than one
fronting something the user would be paged about at 3am. Forcing all tunnels
into one model — either "everything stays local, rebuild by hand if the box
dies" or "everything is control-plane, give up local auditability" —
optimizes for the tool's implementation simplicity, not for the actual range
of things a homelab operator runs. Keeping both modes available, chosen per
tunnel, is more work to build but keeps the tool aligned with how real
homelab usage actually varies.

### The honest counter-argument

Maintaining two management models is a real, ongoing cost: two auth flows,
two sets of failure modes to keep fail-closed, two things to explain in the
Wiki, twice the surface for the kind of subtle bug this project has spent
several TDDs hunting down (locale collation, heredoc injection, exit-code
swallowing). A reasonable alternative philosophy is: pick one model and be
excellent at it, rather than being pretty good at two. This document does
not resolve that tension — it is recorded as the central open question in
[Open Questions and Decision Gates](#open-questions-and-decision-gates).

## Current Architecture Recap: Locally-Managed Tunnels

For contrast, what `cftunnel` does today (all shipped, all tested):

1. `cloudflared tunnel login` — OAuth flow producing a zone-scoped
   `cert.pem` (origin certificate), isolated per zone by CFTUNNEL-002/007.
2. `cloudflared tunnel create` — creates a tunnel and writes a **local**
   credential JSON (`<UUID>.json`) containing the tunnel's private key
   material. This file is generated once and is not retrievable from
   Cloudflare afterward.
3. Ingress configuration lives in a **local YAML file**
   (`~/.cloudflared/zones/<zone>/<name>.yml`), one file per tunnel by
   default, hand-authored by `cftunnel add`.
4. `cloudflared tunnel run --config <yaml>` reads that local file at
   startup and on every restart. One systemd unit per tunnel, matching the
   YAML file it points at.
5. DNS routing (`cloudflared tunnel route dns`) and all discovery
   (CFTUNNEL-008) operate against the `cert.pem`-authenticated `cloudflared`
   CLI, not a direct REST API call.

Every credential in this model is either the zone-scoped origin cert
(recoverable by re-running `zone login`) or the tunnel-scoped credential
JSON (**not** recoverable — this is the gap CFTUNNEL-012 addresses from a
different angle: backing up what can't be regenerated, instead of avoiding
the need for backup in the first place).

## How Remotely-Managed Tunnels Actually Work

Verified against Cloudflare's own documentation before writing this section
(see Sources), not assumed:

- A remotely-managed tunnel's ingress configuration (public hostnames,
  origin services, path rules) is stored in Cloudflare's control plane and
  configured via the dashboard or the REST API — **not** via any
  `cloudflared` CLI subcommand and **not** via a local YAML file that
  `cloudflared` reads at startup.
- The connector (`cloudflared`) only needs a **token** to run:
  `cloudflared service install <TOKEN>` (or `cloudflared tunnel run --token
  <TOKEN>`), which installs it as a background service. On Linux this is
  still a systemd-managed process today, per Cloudflare's own install
  instructions.
- That token can be **rotated/refreshed** via Cloudflare One → Networks →
  Connectors → Cloudflare Tunnels → Edit → "Refresh token", without deleting
  the tunnel or its DNS routes. Existing connections remain active with the
  old token until the connector process is restarted with the new one — so
  rotation is disruption-free if the tunnel is fronted by more than one
  connector replica, and a brief, controlled restart otherwise.
- Cloudflare explicitly recommends rotating tokens on a regular cadence,
  treating rotation as a normal operational action, not an emergency-only
  escape hatch — which is a meaningfully different security posture than
  cftunnel's current "the credential file is precious and irreplaceable."

### What this means for disaster recovery specifically

If the host running a remotely-managed tunnel's connector dies, recovery is:
install `cloudflared`, fetch (or refresh) the token from Cloudflare, run
`cloudflared service install <TOKEN>`. No DNS change, no tunnel recreation,
no dependency on any local backup having been taken. This is strictly better
than the current model's best case (a working encrypted backup restored
correctly) and categorically better than its worst case (no backup, tunnel
recreated from scratch with a new UUID and a DNS update).

### What this does *not* solve

It does not touch resource overhead (still one connector process per tunnel
if that isolation is preserved — see next section), does not touch systemd/
Linux coupling (the connector process still needs *some* process supervisor
on the host), and does not touch cftunnel's zone-scoped local-file model for
anything other than ingress configuration and the tunnel credential
specifically.

## What Would Change vs. What Would Stay

The critical realization from this conversation: locally-managed vs.
remotely-managed is an axis about **where ingress configuration and the
tunnel secret live**, not about **how many processes run or how isolated
they are**. These are independent decisions that the current local-YAML
model happens to bundle together. A remote-managed mode does not force
giving up the one-tunnel-one-systemd-unit isolation this project (and
Gemini's review) values.

| Aspect | Stays the same | Changes |
|---|---|---|
| One systemd unit per tunnel (blast-radius isolation) | Yes — nothing about remote management requires collapsing tunnels into one process | — |
| `cftunnel add/remove/start/stop/status/logs` UX | Yes — same imperative command shape | The implementation behind `add` differs by mode |
| Zone-scoped `cert.pem` (CFTUNNEL-002/007) | Used for locally-managed tunnels | Not used for remotely-managed tunnels at all — a different Cloudflare API Token (Bearer auth, scoped permissions) replaces it for control-plane calls |
| Local YAML as ingress source of truth | Only for locally-managed tunnels | Remotely-managed tunnels have no local ingress YAML; `cftunnel list` would need a different (or dual) data source |
| Tunnel credential recoverability | — | Remotely-managed: token is rotatable via API, recovery does not require a prior backup. Locally-managed: unchanged, still irrecoverable without CFTUNNEL-012 |
| Discovery/creation fail-closed logic (CFTUNNEL-008) | Reusable in spirit | Needs an equivalent for direct REST API calls (today's `discover_tunnel_uuid`/`create_tunnel_uuid` are built around `cloudflared tunnel list/create --output json`, which is locally-managed-oriented) |
| Dependencies | `bash`, `jq`, `cloudflared` | Would add `curl` (or continued exclusive use of `cloudflared`, if it grows a remote-config subcommand — unconfirmed, see [Open Questions](#open-questions-and-decision-gates)) |

## A Possible Additive Shape

Sketched, not specified — this is intentionally lower-resolution than
CFTUNNEL-010's contract, because too much is still unverified to write a
committable interface.

```text
cftunnel add --hostname app.example.com --type http --service http://localhost:8080 [--managed local|remote]
```

- `--managed local` (default, unchanged): today's exact behavior.
- `--managed remote`: creates or reuses a remotely-managed tunnel via the
  Cloudflare API, configures its ingress via the API, installs a systemd
  unit running `cloudflared tunnel run --token <token-file-or-env>` scoped
  to that one tunnel (preserving per-tunnel isolation), and stores only
  non-secret bookkeeping locally (which tunnels exist, their mode) — the
  token itself would need its own credential-handling story, likely modeled
  on the existing zone-credential secrecy/permission conventions
  (CFTUNNEL-002/007) even though the underlying secret type is different.

`cftunnel list` would need to show both kinds of tunnels, or clearly
partition them, since local YAML scanning alone would no longer see
remotely-managed tunnels.

This shape is deliberately incomplete. It exists to make the "additive, not
a rewrite" argument in [Philosophical Considerations](#philosophical-considerations)
concrete enough to evaluate, not to be implemented as written.

## Relationship to Other Design Records

- **CFTUNNEL-010** (TUI integration contract): independent of this
  decision. The `--output json` / `--yes` contract CFTUNNEL-010 specifies
  for `cftunnel list`/`add`/`remove` should work the same way regardless of
  which management mode a given tunnel uses — the TUI talks to `cftunnel`,
  not to Cloudflare's API directly, so this document's outcome is invisible
  to that contract as long as `cftunnel list --output json` accounts for
  both modes if this is ever built.
- **CFTUNNEL-012** (`cftunnel backup`, drafted alongside this document):
  addresses the same disaster-recovery gap from the opposite direction —
  making the current model's irrecoverable secret recoverable via backup,
  rather than changing the model so nothing irrecoverable exists. These are
  not mutually exclusive. If CFTUNNEL-011 is ever implemented as an
  additive mode, CFTUNNEL-012 remains valuable for any tunnel still running
  `--managed local` (which may be most tunnels, by choice, indefinitely —
  see [Philosophical Considerations](#philosophical-considerations)).

## Open Questions and Decision Gates

None of these are resolved. Listed so the next conversation about this
starts here instead of at zero.

### DG-01: One model or two, permanently?

Is "additive, chosen per tunnel" the right end state, or is it a
transitional compromise on the way to eventually deprecating the local
model? This document takes no position — see
[Philosophical Considerations](#philosophical-considerations) for the
argument on each side. **This is the central open question.**

### DG-02: Does `cloudflared` expose a CLI path for remote ingress config, or is direct API access required?

Unconfirmed at the time of writing. If `cloudflared` gains (or already has,
undiscovered) a subcommand for configuring a remotely-managed tunnel's
ingress, that would let this reuse the existing "shell out to `cloudflared`,
never speak HTTP directly" pattern this project has used from the start. If
not, `cftunnel` would need to become an HTTP API client (`curl` + Cloudflare
API Tokens) for the first time. **Must be verified against the actual
`cloudflared` CLI and Cloudflare API docs before any implementation TDD is
written** — do not assume either answer.

### DG-03: What does zone-scoped isolation mean for an API Token instead of a per-zone origin cert?

CFTUNNEL-002/007's entire zone-isolation model is built around one
`cert.pem` per zone with filesystem-level secrecy and binding checks. A
Cloudflare API Token is scoped by *permissions*, not by *zone* in the same
way — need to determine whether a token can be scoped narrowly enough to
preserve the "a compromised zone credential can't touch other zones"
property this project currently guarantees, or whether that guarantee would
weaken under the remote model.

### DG-04: Migration path for existing locally-managed tunnels

If a user wants to move a specific existing tunnel from local to remote
management, what does that command look like, and is it even possible
without recreating the tunnel (new UUID, new DNS target)? Unconfirmed.

### DG-05: How does `cftunnel list` present two kinds of tunnels coherently?

Today's `list` is explicitly local-file-only and offline (AGENTS.md:
"Root-level YAML and the Cloudflare API are not used"). A remotely-managed
tunnel has no local YAML to scan. Reconciling this without turning `list`
into a networked, non-offline command by default is an open design problem.

## Risk Assessment

This is a qualitative risk read for the *idea*, not a shipped feature's risk
matrix (see [What Would Need to Happen Before This Becomes a Real
TDD](#what-would-need-to-happen-before-this-becomes-a-real-tdd) for why a
quantitative one would be premature).

| Risk | Why it matters here |
|---|---|
| Two management models double the fail-closed surface area | Every CFTUNNEL-004/007/008/009-class bug this project has hunted would need its own equivalent audit for the remote path |
| API Token scoping may not match zone-isolation guarantees | Could silently weaken a security property CFTUNNEL-002/007 currently enforce (see DG-03) |
| Direct Cloudflare REST API usage is a new failure/versioning surface | `cloudflared` CLI output contracts are already carefully fixture-tested (CFTUNNEL-008); raw API responses would need the same treatment, and API versioning is Cloudflare's schedule, not this project's |
| Philosophical drift | If "additive" quietly becomes "remote is now required," the project's core differentiator (local auditability) erodes without anyone deciding that on purpose |

## What Would Need to Happen Before This Becomes a Real TDD

In order, before any implementation planning:

1. Resolve DG-02 concretely — read the current `cloudflared` CLI reference
   and Cloudflare API docs for the installed supported version, the same
   evidence-first approach CFTUNNEL-008 used for `--output json` contracts.
2. Prototype the API auth flow manually (create an API Token, call the
   tunnel-configuration endpoint, observe the exact request/response shape)
   before designing any bash implementation around it.
3. Resolve DG-01 as an explicit decision, not a default — this is a project
   direction question, not an engineering one, and deserves a deliberate
   answer from the people building this, not an implicit one from whoever
   writes the first line of code.
4. Only then would a CFTUNNEL-01X implementation TDD, structured like
   CFTUNNEL-010, be appropriate.
